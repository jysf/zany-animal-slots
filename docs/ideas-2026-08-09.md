## Multiplayer / win-multiplier

Concurrency-based payout boost, three options by ambition:

1. **"Hot machine" concurrency multiplier (lightest).** Cloudflare KV
   heartbeat (each tab pings "I'm here" every ~15s, TTL-expired) gives a
   rough live player count; feed it into a small multiplier curve
   (~+1%/player, capped) applied *after* the engine resolves the spin.
   No WebSockets, no persistent connections.
2. **"Spin party" (medium).** A Cloudflare Durable Object + WebSocket hub
   broadcasts presence live; several people spinning in the same window
   triggers a real synchronized-spin bonus pushed instantly. First time
   this app would run an actual server process — today it's pure static
   assets with no Worker `main` at all (`wrangler.jsonc`).
3. **Progressive jackpot pool (most on-genre).** Pool a sliver of every
   spin globally into a shared jackpot any player can trigger — how real
   linked slot machines actually work. Reuses the existing rare-jackpot
   path (Wolf jackpot, trophy-earned moment) rather than touching normal
   win math.

Recommendation: start with #1 to test whether "busier = better payout"
actually resonates before building real-time infra.

Architecture note regardless of option: keep the multiplier **out of the
pure engine** (DEC-001/DEC-002) — apply it as a presentation-layer scalar
on the displayed payout, never thread live network state into the
deterministic resolver.

Bigger-picture flag: this would be the **first cross-player state** this
app has ever had. Everything today (balance, stats, trophies) is local per
DEC-020. Worth its own explicit decision, the way analytics (DEC-023) and
the ad-probe were each deliberately gated rather than added quietly.

## Login/register — early thinking only (not decided, not started)

Explicit tension: everything in this app has always been local-only
(DEC-020) — no accounts, no server, nothing leaves the browser. A
traditional login/register reverses that. Framing explored: lean into
local-only instead of fighting it.

- **Seed phrase as identity (front-runner).** DEC-002 already makes the
  game's randomness a seed you can hold, share, and replay. Apply the same
  idea to identity: a human-readable phrase that deterministically
  represents local state, portable across devices, zero server, zero
  password, zero email.
- **Save export/import.** Simpler fallback — a "download your save" /
  "load a save" button, a user-controlled JSON blob, no portability magic.
- **Device linking / pairing code.** Signal-style temporary pairing
  between two open sessions — no account outlives the pairing.
- **If real accounts are ever needed** (e.g. multiplayer identity): keep
  it strictly additive — the game plays fully forever with zero account;
  login is an opt-in convenience layered on top, never a gate.

## RNG extraction — dig-in findings

`src/engine/rng.ts` is 35 lines, zero dependencies: `createRng(seed)`
(mulberry32) + `randomInt(rng, maxExclusive)`. Used by exactly three files
(`index.ts`, `spin.ts`, `metrics.ts`), always by injection — the
`deterministic-rng` constraint bans `Math.random()` anywhere in the engine,
so this file already has zero coupling to anything else. Mechanically,
extraction is roughly an hour of work.

**The honest gap:** DEC-002 explicitly considered and rejected crypto-grade
randomness — *"Revisit if: we ever need a cryptographically fair draw (we
do not, for play-money)."* What exists is **deterministic and replayable**
(same seed → same spins, provable to yourself), not **provably fair against
an adversary** (nothing stops whoever generates the seed from picking a
flattering one after the fact — fine with no counterparty, not fine for a
raffle, a giveaway, or fair task assignment).

**What a real "provably fair" library needs on top:** keep mulberry32 (or
similar) as the core generator, add a commit-reveal protocol — publish
`hash(serverSeed)` before the outcome-determining action, reveal
`serverSeed` after, combine with a client-supplied seed + nonce so neither
side can unilaterally pick a favorable draw — plus a `verify()` function so
a third party can independently recompute and check. That commit-reveal
layer is the actual interesting engineering; the mulberry32 extraction
itself is closer to a copy-paste.

Recommendation if pursued: legitimately fun, well-scoped weekend build —
core + commit-reveal wrapper, shipped as a tiny zero-dep package with a demo.

## Gambling-mechanics-as-attention-hack — rigorous signal assessment

**Signals for:**
- Real precedent that paced, surprising reveal of dry aggregate data
  reliably drives engagement/sharing where a flat report of the same data
  wouldn't: Spotify Wrapped, GitHub's contribution graph, Duolingo streaks.
  A slot reel is a more intense version of the same reveal mechanic.
- A concrete existence proof from this project, not a hypothetical: the
  rollup number `$108.99 / 12.68M tokens` sat in the lifetime report the
  whole time and completely hid the delegation-collapse story — only
  manual cross-referencing of `cost.sessions[].model` across 100+ files
  surfaced it. Real evidence that meaningful signal gets lost in a plain
  total specifically because nothing rewards looking closely.
- Variable-ratio reinforcement (the core slot-machine mechanism) is one of
  the most robustly studied attention mechanisms in behavioral psychology.
  Pointing it at chronically under-attended data (nobody checks a dashboard
  until something's on fire) is a legitimate transfer, not a random mashup.

**Signals against / risks:**
- Wrapped and the GitHub graph work as *occasional, one-time* reveals, not
  recurring daily-check tools. Slot machines' real power comes from repeat
  play — unproven here.
- Audience mismatch: the person who most needs "your AI's delegation just
  broke" (an eng lead making a call) wants a fast, serious signal, not
  spin-the-reels chrome.
- The actually hard, valuable work this week was the analysis — manually
  cross-referencing model fields, spec IDs, dates, worktree state — not the
  reels. A gambling skin doesn't replace a real anomaly-detection engine;
  it's a thin layer on top of a problem that exists regardless of skin.
- Framing risk: a "jackpot" visual for "we found a cost-drift bug" sends a
  celebratory signal for what's functionally a bug report.

**Verdict:** not crazy — real signal, not just vibes. But the legs are in
the broader genre (paced, surprising reveal of buried anomalies), not
necessarily literally "slot machine" — a Wrapped-style report might land
the same insight with less audience-mismatch risk. Build the
anomaly-detection engine first (valuable regardless of skin); treat the
presentation layer as a separable, testable choice rather than assumed-right
because it fits this project's own aesthetic.
